> 本文档基于对 `yupao-backend-master`（程序员鱼皮原版）完整源码的梳理，
> 并根据 `lin-backend-master` 当前的实际工程状态做了适配。
> 
> **技术栈差异提醒（重要）**：
> 
> | 项           | 鱼皮原版                   | 你的工程                            | 影响                     |

## 〇、总览：真实开发顺序不是线性的

前 6 步是**一次性骨架**，第 7 步之后是**按功能循环迭代**。
每个功能都要走一遍固定套路：

```
定接口(URL/入参/出参) → 写请求类 Request → 写 Service 接口 → 写 Service 实现 → 写 Controller → 自测
```

时间线速查：

```
①  想清楚数据模型（3 张表 + 关系）        ← 最重要的前置思考，错了后面全返工
②  补齐 pom.xml 依赖（按需，别一次全加）
③  搭全局基础设施：BaseResponse → ErrorCode → BusinessException
                    → GlobalExceptionHandler → PageRequest
④  建表 + MyBatis-Plus 逆向生成 实体/Mapper/Service/Controller
⑤  配置层：Swagger(knife4j) / 跨域 / RedisTemplate / Redisson / application.yaml
⑥  【模板功能】用户注册登录 → 打通 Controller→Service→Mapper→DB 全链路
⑦  【迭代】用户功能 8 个，按依赖顺序做
⑧  【准备数据】EasyExcel 导入脚本造测试数据
⑨  【核心】队伍功能 8 个（事务 / 分布式锁 / VO 组装 / QueryWrapper 组合）
⑩  【优化】定时任务缓存预热
⑪  测试 + 部署
```

## 一、先想清楚「数据模型」（代码之前，最优先）

这是整个项目的地基，也是新手最容易跳过、后面返工最多的一步。

### 三张核心表

| 表           | 作用      | 关键设计点                                                                 |
| ----------- | ------- | --------------------------------------------------------------------- |
| `user`      | 用户      | `userPassword` 加盐 MD5、`isDelete` 逻辑删除、`userRole` 权限、`tags` 存 JSON 字符串 |
| `team`      | 队伍      | `userId` 是队长、`status` 三种状态（公开/私有/加密）、`maxNum` 人数上限、`expireTime` 过期    |
| `user_team` | 用户-队伍关系 | **多对多中间表**，没有它做不了「我加入的队伍」和「队伍人数统计」                                    |
| `tag`       | 标签      | 可选，最终没用上（标签直接塞 user 表的 JSON 字段了）                                      |

### 建表前先回答这三个问题

答案直接决定表结构：

1. **一个用户能加入几个队伍？** → 多对多 → 必须有 `user_team` 中间表
2. **队伍过期怎么办？** → 必须有 `expireTime` 字段，查询时过滤掉过期的
3. **加密队伍怎么校验？** → 必须有 `status`（区分公开/私有/加密）+ `password` 两个字段

### 建表 SQL 要点

```sql
-- user 表关键字段
userPassword varchar(512) not null comment '密码',
userStatus   int default 0 not null comment '状态 0 - 正常',
createTime   datetime default CURRENT_TIMESTAMP comment '创建时间',
updateTime   datetime default CURRENT_TIMESTAMP on update CURRENT_TIMESTAMP,
isDelete     tinyint default 0 not null comment '是否删除',
userRole     int default 0 not null comment '用户角色 0 - 普通 1 - 管理员',
planetCode   varchar(512) comment '星球编号',
tags         varchar(1024) comment '标签 json 列表'   -- 注意：存 JSON 字符串，不是关联表

-- team 表关键字段
userId     bigint comment '用户id（队长 id）',
maxNum     int default 1 not null comment '最大人数',
expireTime datetime comment '过期时间',
status     int default 0 not null comment '0-公开，1-私有，2-加密',
password   varchar(512) comment '密码'

-- user_team 关系表
userId   bigint comment '用户id',
teamId   bigint comment '队伍id',
joinTime datetime comment '加入时间'
```

> **注意你的 `sql/creat_table.sql` 现在只有一句 `create database partern;`**，
> 而且数据库名 `partern` 疑似 `partner` 拼写错误。建议先确认库名，再补全三张表。
> 目录里是 `lin伙伴匹配`，下面文档统一按 `partner` 举例，**你按实际库名改**。

## 二、补齐 pom.xml 依赖（按需，别一次全加）

你的工程目前**只有** `mybatis-spring-boot-starter` + `lombok` + `devtools` + `test`。
和原版相比，缺少下面这些 —— 但**不要一次性全加**，写一个功能加一个依赖。

| 依赖                                             | 版本        | 用途                                                          | 什么时候加   |
| ---------------------------------------------- | --------- | ----------------------------------------------------------- | ------- |
| `mybatis-plus-boot-starter`                    | 见下方注意     | ORM + 分页 + 逻辑删除 + CRUD，**替代原生 mybatis-spring-boot-starter** | 第 ④ 步   |
| `mysql-connector-j`                            | 由 Boot 管理 | MySQL 驱动                                                    | 第 ④ 步   |
| `knife4j-openapi3-jakarta-spring-boot-starter` | 4.x       | 接口文档（Boot 3/4 用 jakarta 版）                                  | 第 ⑤ 步   |
| `commons-lang3`                                | 3.12.0    | `StringUtils` 字符串工具                                         | 写注册功能时  |
| `commons-collections4`                         | 4.4       | `CollectionUtils` 集合工具                                      | 写队伍列表时  |
| `gson`                                         | 2.8.9     | 解析 `tags` JSON                                              | 搜索标签功能时 |
| `spring-boot-starter-data-redis`               | —         | 缓存                                                          | 推荐用户功能时 |
| `spring-session-data-redis`                    | —         | Session 存 Redis（分布式登录态）                                     | 登录功能时   |
| `redisson-spring-boot-starter`                 | 3.x       | 分布式锁                                                        | 加入队伍时   |
| `easyexcel`                                    | 3.1.0     | 导入 Excel 造数据                                                | 造测试数据时  |

### Boot 4 下的依赖注意事项

1. **MyBatis-Plus 要用支持 Boot 3/4 的版本**。
   老版本 `3.5.1` 只支持 Spring Boot 2.x，直接引入会启动失败。
   建议用 `com.baomidou:mybatis-plus-spring-boot3-starter`（3.5.5+），
   或在 [MP 官网](https://baomidou.com/getting-started/) 确认当前适配 Boot 4 的版本号。

2. **引入 MyBatis-Plus 后要移除原生 `mybatis-spring-boot-starter`**，
   否则两套 SqlSessionFactory 会冲突。

3. **`javax.*` → `jakarta.*`**：Boot 4 中 Servlet API 全部迁移到 jakarta。
   原版代码里的 `javax.servlet.http.HttpServletRequest`、`javax.annotation.Resource`
   在你的工程里必须改成 `jakarta.servlet.http.HttpServletRequest`、`jakarta.annotation.Resource`。

## 三、全局基础设施（比 CRUD 更早，因为后面全要用）

**先搭地基再写业务**，否则每个 Controller 都要重复写错误处理。顺序不能反：

```
① 定义错误码 → ② 定义异常 → ③ 定义异常处理器 → ④ 定义统一返回体
```

| 顺序  | 文件                                      | 作用                                                                                                                                                                                 |
| --- | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `common/ErrorCode.java`                 | 错误码枚举：`SUCCESS(0)` / `PARAMS_ERROR(40000)` / `NULL_ERROR(40001)` / `NOT_LOGIN(40100)` / `NO_AUTH(40101)` / `FORBIDDEN(40301)` / `SYSTEM_ERROR(50000)`，每个含 code/message/description |
| 2   | `exception/BusinessException.java`      | 继承 `RuntimeException`，带 code/message/description，支持 `(ErrorCode)` 和 `(ErrorCode, String)` 两种构造                                                                                     |
| 3   | `common/BaseResponse.java`              | 统一返回体：`code` / `data` / `message` / `description`，泛型 `<T>`                                                                                                                         |
| 4   | `common/ResultUtils.java`               | 工具类：`success(T data)` / `error(ErrorCode)` / `error(int, String, String)`                                                                                                          |
| 5   | `exception/GlobalExceptionHandler.java` | `@RestControllerAdvice`，把 `BusinessException` 和 `RuntimeException` 统一转成 `BaseResponse`                                                                                             |
| 6   | `common/PageRequest.java`               | 通用分页参数：`pageSize = 10` / `pageNum = 1`                                                                                                                                             |
| 7   | `common/DeleteRequest.java`             | 通用删除请求：只有一个 `long id`                                                                                                                                                              |

### 建议的包结构

## 四、建表 + MyBatis-Plus 逆向生成 CRUD

### 步骤

1. **执行建表 SQL**，建库建表
2. **配置 `application.yaml`**：
   - 数据源（url / username / password）
   - MyBatis-Plus 的 `map-underscore-to-camel-case: false`（**注意是 false**，因为字段名本身就是驼峰）
   - 全局逻辑删除配置
3. **用 MyBatisX 插件或 `AutoGenerator` 生成**：
   - `model/domain/User.java`、`Team.java`、`UserTeam.java`（实体）
   - `mapper/UserMapper.java` 等 —— 继承 `BaseMapper<T>`，**方法体一行代码都不用写**
   - `service/UserService.java` + `UserServiceImpl` —— 继承 `IService<T>` / `ServiceImpl<Mapper, T>`
   - `controller/UserController.java` —— 骨架

### 生成后必须手工调整的地方

- 实体类加 `@TableName("user")`、`@TableId(type = IdType.AUTO)`
- `isDelete` 字段加 `@TableLogic`
- 启动类 `LinBackendMasterApplication` 加 `@MapperScan("com.xlingsbx.linbackendmaster.mapper")`
- **`MybatisPlusConfig` 注册分页插件**：
  
  ```java
  @Bean
  public MybatisPlusInterceptor mybatisPlusInterceptor() {
      MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
      interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
      return interceptor;
  }
  ```
  
  > **不加分页插件，`page()` 会静默失效** —— 不报错，但返回全部数据。

### ⚠️ 关于代码生成器的重要认知

自动生成的 Controller（那套 list/get/add/update/delete）**在真实项目里几乎全被删掉**。
真实业务的接口是自定义的（`/user/register`、`/team/join`）。

**生成器真正的价值**是帮你省掉：

- 实体类 + 字段注释的样板
- Mapper 接口 + 对应 XML

而 `BaseMapper` 提供的 `selectById` / `save` / `updateById` / `list` / `page` / `count`，
才是后面业务代码里**真正反复复用**的东西。别指望它生成业务接口。

## 六、第一个功能：用户注册 / 登录（纵向打通全链路）

这是一个**「模板功能」** —— 跑通它，后面所有功能都是复制这套模式。

### 四层流程

```
1. 定义请求类  model/request/UserRegisterRequest.java   （@Data）
2. 定义接口    service/UserService.java
3. 写实现      service/impl/UserServiceImpl.java
4. 写接口      controller/UserController.java
```

### Service 层的标准套路（每个业务方法都长这样）

```
① 校验参数是否为空 / 长度是否合法
② 业务规则校验（账号不能含特殊字符、账号不能重复、星球编号不能重复）
③ 处理数据（MD5 加盐加密）
④ 落库（this.save(user)）
⑤ 返回
```

注册的核心代码：

```java
// 盐值
private static final String SALT = "yupi";

// 账户不能包含特殊字符
String validPattern = "[`~!@#$%^&*()+=|{}':;',\\[\\].<>/?~！@#￥%……&*（）——+|{}【】'；：\"\"'。，、？]";
Matcher matcher = Pattern.compile(validPattern).matcher(userAccount);
if (matcher.find()) { return -1; }

// 加密
String encryptPassword = DigestUtils.md5DigestAsHex((SALT + userPassword).getBytes());

// 插入
User user = new User();
user.setUserAccount(userAccount);
user.setUserPassword(encryptPassword);
user.setPlanetCode(planetCode);
boolean saveResult = this.save(user);
```

### 登录的额外三步（本项目用 Session，不是 JWT）

1. 校验账号密码 → `selectOne(queryWrapper)` 查出 user
2. **脱敏 `getSafetyUser(user)`** —— 把 `userPassword` 置空，**绝不能返回给前端**
3. `request.getSession().setAttribute(USER_LOGIN_STATE, safetyUser)` —— 记录登录态

```java
public User getSafetyUser(User originUser) {
    if (originUser == null) return null;
    User safetyUser = new User();
    safetyUser.setId(originUser.getId());
    safetyUser.setUsername(originUser.getUsername());
    // ... 逐个字段复制，就是不复制 userPassword
    return safetyUser;
}
```

### 踩坑点

- `@CrossOrigin(origins = {"http://localhost:3000"})` 和 `WebMvcConfg` 里都配了跨域
- `session.cookie.domain=localhost` 必须配，否则前端跨端口（3000 → 8080）带不上 cookie
- 用 `@CrossOrigin` + `allowCredentials` 时，`allowedOrigins` **不能写 `*`**，必须写具体域名

## 七、用户功能迭代（按依赖顺序，逐个加）

每个功能都走第六步那套「四层流程」。因为后一个依赖前一个，顺序不能乱：

| #   | 功能       | 接口                      | 关键技术点                                                                                          |
| --- | -------- | ----------------------- | ---------------------------------------------------------------------------------------------- |
| 1   | 获取当前登录用户 | `GET /user/current`     | 从 Session 取 `USER_LOGIN_STATE`，取出 userId 后再查库（避免用旧数据）                                          |
| 2   | 管理员查询用户  | `GET /user/search`      | `isAdmin(request)` 权限校验，非管理员抛 `PARAMS_ERROR`                                                   |
| 3   | 用户注销     | `POST /user/logout`     | `request.getSession().removeAttribute(USER_LOGIN_STATE)`                                       |
| 4   | 更新用户信息   | `POST /user/update`     | **只有本人或管理员能改**（水平越权防护）：`if (!isAdmin(loginUser) && userId != loginUser.getId()) throw NO_AUTH` |
| 5   | 删除用户     | `POST /user/delete`     | 仅管理员；`removeById(id)`                                                                          |
| 6   | 按标签搜索用户  | `GET /user/search/tags` | **先写内存过滤版**：Gson 解析 tags → stream filter。再写 SQL like 版并标 `@Deprecated` 保留对比                    |
| 7   | 推荐用户（分页） | `GET /user/recommend`   | Redis 缓存：**先查缓存 → 无则查库 → 写缓存**，用 try-catch 包住 redis 操作                                         |
| 8   | 编辑距离匹配用户 | `GET /user/match`       | `AlgorithmUtils.minDistance` 动态规划算标签相似度，排序取 TopN                                               |

### 第 6 步的两种实现（强烈建议都写）

**内存过滤版（推荐，实际使用）：**

```java
List<User> userList = userMapper.selectList(new QueryWrapper<>());  // 1. 查所有用户
Gson gson = new Gson();
return userList.stream().filter(user -> {
    Set<String> tempTagNameSet = gson.fromJson(user.getTags(), new TypeToken<Set<String>>(){}.getType());
    tempTagNameSet = Optional.ofNullable(tempTagNameSet).orElse(new HashSet<>());
    for (String tagName : tagNameList) {
        if (!tempTagNameSet.contains(tagName)) return false;
    }
    return true;
}).map(this::getSafetyUser).collect(Collectors.toList());
```

**SQL like 版（标 `@Deprecated`）：**

```java
for (String tagName : tagNameList) {
    queryWrapper = queryWrapper.like("tags", tagName);   // like '%Java%' and like '%Python%'
}
```

> **学习价值**：先实现能跑的版本 → 再优化 → 旧版标 `@Deprecated` 留着对比，
> 而不是直接删掉。能直观感受「SQL 模糊匹配」和「内存精确过滤」的差异与坑。

### 第 7 步：Redis 缓存的标准写法

```java
User loginUser = userService.getLoginUser(request);
String redisKey = String.format("lin:user:recommend:%s", loginUser.getId());
ValueOperations<String, Object> valueOperations = redisTemplate.opsForValue();

// 1. 有缓存直接读
Page<User> userPage = (Page<User>) valueOperations.get(redisKey);
if (userPage != null) return ResultUtils.success(userPage);

// 2. 无缓存查数据库
userPage = userService.page(new Page<>(pageNum, pageSize), new QueryWrapper<>());

// 3. 写缓存（一定要 try-catch —— 缓存挂了不能影响主流程）
try {
    valueOperations.set(redisKey, userPage, 30000, TimeUnit.MILLISECONDS);
} catch (Exception e) {
    log.error("redis set key error", e);
}
```

### 第 8 步：编辑距离匹配用户

```java
// 1. 只查 id 和 tags 两列（不要 select *，省传输）
QueryWrapper<User> queryWrapper = new QueryWrapper<>();
queryWrapper.select("id", "tags");
queryWrapper.isNotNull("tags");
List<User> userList = this.list(queryWrapper);

// 2. 依次计算相似度（编辑距离，越小越相似）
for (User user : userList) {
    if (StringUtils.isBlank(user.getTags()) || user.getId() == loginUser.getId()) continue;
    long distance = AlgorithmUtils.minDistance(tagList, userTagList);
    list.add(new Pair<>(user, distance));
}

// 3. 排序取 TopN，收集 userId 列表
List<Long> userIdList = list.stream()
        .sorted((a, b) -> (int) (a.getValue() - b.getValue()))
        .limit(num).map(pair -> pair.getKey().getId()).collect(Collectors.toList());

// 4. 按 id 批量查（一次 IN 查询），再按 userIdList 顺序重排
```

> **注意**：`userIdList` 的**顺序就是匹配度顺序**，但 `IN` 查询返回的顺序是数据库顺序。
> 所以必须用 `Map<Long, List<User>>` 做映射，再按 `userIdList` 遍历重排，否则排序白做了。

## 九、队伍功能（最复杂，综合运用前面所有技术）

**开发顺序有讲究**：必须先有队伍，才能加入 / 退出。

| #   | 功能       | 接口                         | 关键技术点                                                        |
| --- | -------- | -------------------------- | ------------------------------------------------------------ |
| 1   | 创建队伍     | `POST /team/add`           | `@Transactional` **同时插 `team` + `user_team` 两张表**；校验最多创建 5 个 |
| 2   | 查询队伍列表   | `GET /team/list`           | 一堆 `QueryWrapper` 组合条件；关联查队长信息；**不展示已过期队伍**；普通用户查不到私有队伍      |
| 3   | 更新队伍     | `POST /team/update`        | 只有队长或管理员能改                                                   |
| 4   | **加入队伍** | `POST /team/join`          | **Redisson 分布式锁**保证并发安全；加密队伍校验密码；私有队伍禁止加入                    |
| 5   | 退出队伍     | `POST /team/quit`          | `@Transactional`；剩 1 人直接解散；**队长退出要把队长转移给最早加入的人**             |
| 6   | 解散队伍     | `POST /team/delete`        | `@Transactional`，**先删 `user_team` 关联，再删队伍**                  |
| 7   | 我创建的队伍   | `GET /team/list/my/create` | `teamQuery.setUserId(loginUser.getId())` 复用 listTeams        |
| 8   | 我加入的队伍   | `GET /team/list/my/join`   | 先查 `user_team` 拿 teamId 列表，再 `setIdList` 复用 listTeams        |

### 创建队伍：事务 + 双表插入

```java
@Override
@Transactional(rollbackFor = Exception.class)   // 必须指定 rollbackFor
public long addTeam(Team team, User loginUser) {

    // 5. 校验：该用户创建队伍数 < 5

    team.setUserId(userId);
    boolean result = this.save(team);
```

### 查询队伍列表：几个精髓点

```java
// 1️⃣ 搜索关键词同时对 name 和 description 做 or 查询（用 lambda 包住，防止 or 优先级污染其他条件）
if (StringUtils.isNotBlank(searchText)) {
    queryWrapper.and(qw -> qw.like("name", searchText).or().like("description", searchText));
}

// 2️⃣ 不展示已过期的队伍
queryWrapper.and(qw -> qw.gt("expireTime", new Date()).or().isNull("expireTime"));

// 3️⃣ 普通用户不能查私有队伍
if (!isAdmin && statusEnum.equals(TeamStatusEnum.PRIVATE)) {
    throw new BusinessException(ErrorCode.NO_AUTH);
}
queryWrapper.eq("status", statusEnum.getValue());

// 4️⃣ 关联查询创建人信息 → 装进 TeamUserVO
for (Team team : teamList) {
    User user = userService.getById(team.getUserId());
    TeamUserVO teamUserVO = new TeamUserVO();
    BeanUtils.copyProperties(team, teamUserVO);
    if (user != null) {
        UserVO userVO = new UserVO();
        BeanUtils.copyProperties(user, userVO);   // UserVO 不带密码，天然脱敏
        teamUserVO.setCreateUser(userVO);
    }
    teamUserVOList.add(teamUserVO);
}
```

> **`queryWrapper.and(qw -> ...)` 的用法非常关键**：
> 直接写 `queryWrapper.like("name", x).or().like("description", x)` 会让 `or` 影响
> 前面所有条件（变成 `A and B or C`），必须用 lambda 包成一个整体 `A and (B or C)`。

### 加入队伍：Redisson 分布式锁（本项目最核心的并发点）

```java
RLock lock = redissonClient.getLock("lin:join_team");
try {
    while (true) {
        // waitTime=0：拿不到锁立即返回 false；leaseTime=-1：启用看门狗自动续期
        if (lock.tryLock(0, -1, TimeUnit.MILLISECONDS)) {
            // ⚠️ 下面三个校验必须在锁内，否则并发下会超员
            // ① 该用户已加入队伍数 <= 5
            // ② 该用户未加入过这个队伍
            // ③ 队伍当前人数 < maxNum
            UserTeam userTeam = new UserTeam();
            userTeam.setUserId(userId);
            userTeam.setTeamId(teamId);
            userTeam.setJoinTime(new Date());
            return userTeamService.save(userTeam);
        }
    }
} catch (InterruptedException e) {
    log.error("doCacheRecommendUser error", e);
    return false;
} finally {
    // 只能释放自己持有的锁
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

> **原版这里有个设计瑕疵**：`tryLock(0, -1)` 拿不到锁时返回 false，代码却没 `break`，
> 于是 `while(true)` 会**忙等自旋**，CPU 空转。学习时建议改成 `tryLock(0, -1)` 失败就
> `throw new BusinessException(ErrorCode.SYSTEM_ERROR, "系统繁忙")`，或加 `Thread.sleep`。

### 退出队伍：队长转移逻辑（最绕的一段）

```java
long teamHasJoinNum = countTeamUserByTeamId(teamId);

if (teamHasJoinNum == 1) {
    // ① 只剩一人 → 直接解散
    this.removeById(teamId);
} else {
    // ② 还有其他人
    if (team.getUserId() == userId) {          // 退出的是队长
        // 把队长转移给「最早加入的用户」= 关系表里 id 最小的第二个（第一个是队长自己）
        QueryWrapper<UserTeam> qw = new QueryWrapper<>();
        qw.eq("teamId", teamId);
        qw.last("order by id asc limit 2");     // 取前两条
        List<UserTeam> list = userTeamService.list(qw);
        UserTeam nextUserTeam = list.get(1);    // 索引 0 是队长自己，取 1
        // 更新队伍的 userId
        Team updateTeam = new Team();
        updateTeam.setId(teamId);
        updateTeam.setUserId(nextUserTeam.getUserId());
        this.updateById(updateTeam);
    }
}
// ③ 最后移除关系
return userTeamService.remove(queryWrapper);
```

### 两个贯穿全项目的设计精髓

**① DTO 复用** —— `TeamQuery` 一个类服务三个接口：

| 接口                     | 差异化设置                                                      |
| ---------------------- | ---------------------------------------------------------- |
| `/team/list`           | 直接用前端传来的参数                                                 |
| `/team/list/my/create` | `teamQuery.setUserId(loginUser.getId())`                   |
| `/team/list/my/join`   | 先查 `user_team` 拿 teamId 列表 → `teamQuery.setIdList(idList)` |

避免写三个 90% 重复的接口。

**② VO 承载「接口需要的所有字段」** —— `TeamUserVO`：

- 队伍自身字段（id / name / description / maxNum / expireTime / status ...）
- `createUser`（队长信息，`UserVO` 类型，天然脱敏）
- `hasJoin`（**当前用户是否已加入**，数据库里没有）
- `hasJoinNum`（**已加入人数**，数据库里没有）

后两个是**组装**出来的，不是查出来的。这是 VO 存在的意义。

而且这两个字段是在 **Controller 层**填充的，不是在 Service 层：

```java
// TeamController.listTeams()
List<TeamUserVO> teamList = teamService.listTeams(teamQuery, isAdmin);

// 2、批量判断当前用户是否已加入（一次 IN 查询，不是循环查）
QueryWrapper<UserTeam> userTeamQueryWrapper = new QueryWrapper<>();
userTeamQueryWrapper.eq("userId", loginUser.getId());
userTeamQueryWrapper.in("teamId", teamIdList);
Set<Long> hasJoinTeamIdSet = userTeamService.list(userTeamQueryWrapper).stream()
        .map(UserTeam::getTeamId).collect(Collectors.toSet());
teamList.forEach(team -> team.setHasJoin(hasJoinTeamIdSet.contains(team.getId())));

// 3、批量统计已加入人数（一次查询 + 分组，不是循环 count）
Map<Long, List<UserTeam>> teamIdUserTeamList = userTeamService.list(joinQw).stream()
        .collect(Collectors.groupingBy(UserTeam::getTeamId));
teamList.forEach(team -> team.setHasJoinNum(
        teamIdUserTeamList.getOrDefault(team.getId(), new ArrayList<>()).size()));
```

> **重点**：这里是**批量查询 + 内存分组**，而不是 `for` 循环里逐个 `count()`。
> 循环里查库 = N 次数据库往返（N+1 问题），必须避免。

## 十、缓存预热（最后一步，性能优化）

`job/PreCacheJob.java`：

```java
@Component
@Slf4j
public class PreCacheJob {

    @Resource private UserService userService;
    @Resource private RedisTemplate<String, Object> redisTemplate;
    @Resource private RedissonClient redissonClient;

    /** 重点用户 */
    private final List<Long> mainUserList = Arrays.asList(1L);

    /** 每天凌晨执行，预热推荐用户 */
    @Scheduled(cron = "0 31 0 * * *")
    public void doCacheRecommendUser() {
        RLock lock = redissonClient.getLock("lin:precachejob:docache:lock");
        try {
            if (lock.tryLock(0, -1, TimeUnit.MILLISECONDS)) {
                for (Long userId : mainUserList) {
                    Page<User> userPage = userService.page(new Page<>(1, 20), new QueryWrapper<>());
                    String redisKey = String.format("lin:user:recommend:%s", userId);
                    redisTemplate.opsForValue().set(redisKey, userPage, 30000, TimeUnit.MILLISECONDS);
                }
            }
        } catch (InterruptedException e) {
            log.error("doCacheRecommendUser error", e);
        } finally {
            if (lock.isHeldByCurrentThread()) lock.unlock();
        }
    }
}
```

### 四个关键点

1. **启动类必须加 `@EnableScheduling`** —— 最容易忘，忘了定时任务**静默不执行**，不报任何错
2. Redis key 里带 userId —— 每个用户的推荐列表是独立的
3. 加 Redisson 锁 —— 多实例部署时只有一个节点执行，避免重复刷缓存
4. **缓存过期时间 < 定时任务间隔** —— 这里是 30000ms（30 秒）但每天才跑一次？
   原版这里其实是 `30000` 秒（约 8.3 小时），刚好卡在两次任务之间，是个经验值

## 附录：三条最重要的经验

1. **地基先行**
   错误码体系、统一返回体、异常处理，必须在写第一个业务接口**之前**就定型。
   否则后期每加一个接口都要改一遍返回格式，前端跟着全改。

2. **纵向打通优于横向铺开**
   先用「注册登录」这一个功能把 `Controller → Service → Mapper → DB` 四层走通，
   后面所有功能都是复制这套模式。不要一上来就把三张表的 CRUD 全生成出来。

3. **依赖按需加**
   Redis、Redisson、EasyExcel 都是**对应功能开发时**才引入的，不是一开始全堆进 `pom.xml`。
   一次性加满依赖的后果是：启动变慢、版本冲突排查困难、不知道哪个依赖是干嘛的。
